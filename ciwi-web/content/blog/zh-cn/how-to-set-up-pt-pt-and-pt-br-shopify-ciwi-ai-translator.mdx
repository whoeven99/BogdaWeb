如果你的店铺同时覆盖葡萄牙和巴西，只添加一个 “Portuguese” 通常是不够的。pt-PT 和 pt-BR 虽然接近，但在词汇、语气、商品表达和搜索习惯上，差异已经足以要求你把它们分开处理。

这件事不只影响 storefront 文案，也同样影响 SEO。

<Callout title="核心原则">
  <p>把 pt-PT 和 pt-BR 当成两个独立的运营 locale。它们可以共享一部分基础语言资产，但不应该共用同一套最终审核标准、同一套 glossary 规则，或同一套 SEO 假设。</p>
</Callout>

## 为什么这两个葡语版本要分开

很多团队一开始会想：先翻出一个葡语版本，再同时给葡萄牙和巴西用。实际落地后，问题通常会出现在三个地方：

- 某些表达在其中一个市场听起来不自然
- 搜索关键词习惯并不完全相同
- URL、元数据和 hreflang 信号需要更明确的市场区分

哪怕句子级别差异看起来不大，当用户继续浏览商品页、导航、blog 和结账相关内容时，这种“不够本地”的感觉还是会慢慢累积起来。

## 先在 Shopify 层把市场关系想清楚

在正式跑翻译任务之前，先把 Shopify 里的市场和语言层定义清楚。

更实际地说，就是先确认：

1. 葡萄牙和巴西是否会被当作两个独立市场目标来管理。
2. 两个市场各自的本地化 URL 会如何暴露。
3. 发布流程是否彼此独立，避免一个市场还没审完，另一个市场就被一起推上线。

具体 URL 长什么样，取决于你的 Shopify Markets 配置。但治理原则是稳定的：每个 locale 都应该有自己的可发现路径，也应该有自己的语言定位信号。

## 第一步：在 Ciwi 的 Language 页面同时加入 pt-PT 和 pt-BR

进入 Ciwi 的 **Language** 页面，把两个葡语目标都加入语言配置。当前的语言页就是语言级翻译覆盖和发布状态的管理入口。

这样做很重要，因为你不会希望 pt-BR 的发布节奏被 pt-PT 绑住，反过来也一样。

## 第二步：在第一次大批量翻译前先做 glossary

当两种语言彼此接近时，glossary 反而更重要。

原因很简单：如果没有约束，模型很容易把细微差异“抹平”，最后产出一种技术上能看懂、但市场感很弱的泛葡语版本。

优先锁定这些内容：

- 品牌名
- 产品线名称
- 重复出现的促销表达
- 对市场很敏感的零售用语
- 在葡萄牙和巴西应该故意区分开的词

目标不是建一份很大的字典，而是先防止高价值词在两个葡语版本之间来回漂移。

## 第三步：在 Translate v4 里为两个 locale 分别生成任务

Ciwi 支持一次选择多个目标语言，但每个语言会被拆成独立任务。对 pt-PT 和 pt-BR 来说，这正是更合理的行为。

它的好处是：

- 每个 locale 可以单独观察进度
- 其中一个版本需要重跑时，不用把另一个一起重跑
- 可以并排比较两个输出
- 即使其中一个审核还没完成，也不会卡住另一个的发布

从运营角度看，这比把两个市场塞进一个不透明的大任务里要干净得多。

## 第四步：审核标准也要分开

很多团队虽然把两个 locale 分开生成了任务，但在审核时又把差异抹掉了。

如果审核者只看“是不是能看懂的葡语”，那 pt-PT 和 pt-BR 很快又会被拉回成一个泛化版本。更有效的审核标准应该明确检查：

- 词汇差异
- 促销表达差异
- 货币和市场语境
- 导航命名
- 高流量 SEO 页面和 blog 标题

这一步尤其应该优先检查合集页、核心商品页、帮助内容和 blog 文章。

## 第五步：SEO 层也必须分开处理

很常见的错误是：正文分开了，但 SEO 层仍然共用。

对 pt-PT 和 pt-BR 来说，下面这些都应该作为独立资产审查：

- meta title
- meta description
- page 或 article handle
- canonical 指向
- hreflang 标注
- sitemap 可发现性

如果两个 locale 共用同一套元数据逻辑和 URL 假设，搜索引擎接收到的市场信号就会变弱，用户看到的表达也更容易像“从另一个地区拷过来”的版本。

## pt-PT 和 pt-BR 的 URL 策略怎么定

把两个 locale 分开，并不代表所有 handle 都必须翻成不同版本。但你必须先有一套规则。

一套更实用的规则通常是：

- 只有在关键词表达几乎一致时，才共享 handle
- 只有当市场表达明显不同，才分别本地化 handle
- 任何既有已索引 URL 的修改，都要先准备重定向映射
- handle、title 和 meta description 必须在 locale 级保持一致

这样做可以把 SEO 工作集中在真正有价值的地方，而不是制造表面上的“全部都不同”。

## 最容易避免的几个错误

### 把两个市场当成一个葡语任务

这样会直接丢掉你最需要的运营清晰度。独立任务更容易重试、审核和发布。

### 盲目共用一套 glossary

共享基础 glossary 没问题，但共享最终措辞策略，通常就不够了。

### 忘了 blog 和 SEO 层

很多团队会检查商品页，却漏掉 blog 标题、article handle 和元数据。这样就算 storefront 文案过关，本地搜索匹配度也还是会偏弱。

### 还没做 locale QA 就提前发布

正因为这两种语言很接近，很多不够自然的差异才更容易被忽略。这也是为什么更需要明确的市场级 QA。

## 一套更稳的上线顺序

如果你想把这件事做得更顺，可以按下面的顺序来：

1. 在 **Language** 页面加入 pt-PT 和 pt-BR。
2. 先定义哪些 glossary 词条应该共享，哪些词必须区分。
3. 在 **Translate v4** 中创建两个 locale 的翻译任务。
4. 在 **Manage Translation** 里分别审查两个输出。
5. 只有在市场级 QA 完成后，再发布其中一个或两个语言。
6. 最后检查本地化 URL、元数据、hreflang 和 sitemap 覆盖。

这样做能把两套葡语版本真正分开，又不会把流程推向过重的人工操作。
