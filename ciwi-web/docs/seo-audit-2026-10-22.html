Ciwi.ai SEO 检测报告

检测时间 2026-10-22 · 对象 https://ciwi.ai · Next.js 15 + App Router + 文件化 MDX 内容 · 版本 commit 工作区
一句话结论：技术底座（规范、hreflang、canonical、sitemap 卫生、CI 守门）在同类站点里属于上游水平，几乎没有低级错误； 真正的问题在内容结构层：占全站 77% 的关键词页，在数据层只有 167 份不同正文，却被 535 个关键词各建一页。

诊断修正（2026-10-22 复检）：本报告初版把问题描述为「535 个页面完全重复」并不准确。深入 data 层后发现： 535 条的 title / scenarioDescription / aiPrompt 每条都唯一，真正重复的是 howToSolve 与 faqs —— 全站只有 167 份，平均被 3.2 个关键词复用，最坏 11 个关键词共用同一份解决步骤。 因此页面相似度高（92%–97%）是「同簇共用正文 + 站点骨架 + 同簇推荐卡片」三者叠加的结果，而非整页复制。

三、P0：必须立刻处理

P0-1 1,304 个关键词页互相重复 92%–97% — 规模化内容滥用风险

抽样 shopify-product-research-tool / shopify-product-research-app / find-winning-products-for-shopify 三页做正文比对：

页面正文词数独有词页间相似度

研究工具页 vs 选品页977 / 979597.2%

差异只剩：H1 措辞互换、正文里替换一个动词短语、推荐模块内容重叠。导航、CTA、FAQ、页脚 100% 相同。

但根因不在模板，在数据 —— 全量 535 条字段级统计

同一簇 5 条抽样，aiPrompt 的「Use these inputs」与「Return」两段逐字相同：

这决定了修复方式：簇内每条唯一的数据只有 title 一个字段，howToSolve、faqs、aiPrompt 的输入与产出全部重合。 也就是说 数据里不存在可供差异化提取的真实语义素材。若用模板/同义词改写去「差异化」，产出的是 spun content， Google 对这类内容的处置比原文重复更重。

可行路径只有三条：① 按 167 簇合并为规范页 + 301（结构上真实去重）；② 投入真实撰写，为 535×2 语言逐条写出不同的运营流程；③ 先降低共模板比（保持 535 页但压缩共享样板、跨簇推荐）。

建议：优先 ①，因为它一次性解决重复、抓取预算与同簇自相竞争，且不需要编造内容。② 只有在确认这批长尾词确有独立搜索需求时才值得投入。

P0-2 Meta description 普遍超长，被搜索引擎截断

位置实测长度上限参考结果
首页 description204 字符~155尾部约 30% 被截断
关键词页 description357–363 字符~155超过 2 倍，几乎必被截断或改写
Blog 文章均值 164 字符，7/10 超限~15510 篇里 7 篇超限

现有 buildPageMetadata 已经只对 title 做了 SERP 宽度截断（见 truncateTitleToSERPWidth），description 完全没有保护——这是同一个 helper 里的对称性缺口。

建议：在 src/lib/seo/metadata.ts 补一个 truncateDescription(text, maxChars=155)，按中英文字符分别计数（中文按 2 字符宽），在词边界或句边界截断。同时在 validate-content.mjs 里加规则：frontmatter description > 160 字符直接报错，和现有 frontmatter 校验同级。

P0-3 全站零静态化：43/43 页面 force-dynamic

根因不在页面，而在架构：middleware.ts 用 header 注入语言（x-ciwi-locale）+ rewrite，而不是用 /[locale]/ 路由段。任何读 headers() 的页面都无法预渲染，因此 all pages 被迫 force-dynamic。

页面TTFB总耗时

/blog/0.732s1.036s
/zh-cn/blog/0.720s1.030s

/sitemap.xml（1691 条）—1.525s

每次访问都要完整服务端渲染 + 可能查库，也无法被 CDN 缓存，直接影响 LCP 与抓取速度。Googlebot 抓 1691 个 URL 的成本显著高于静态站。

建议：中长期把 i18n 迁到 App Router 的 /[locale]/ 路由段（generateStaticParams + ISR），彻底摆脱 header 依赖；短期可行的折中是让 mid 层 rewrite 之外的内容类路由（blog / help-center / guides）走 revalidate，至少恢复增量静态。

四、P1：重要，一个月内处理

P1-1 Sitemap lastmod 覆盖率仅 12.4%（209 / 1,691）

只有 blog / help-center / 部分 guides 带 lastModified，其余全部缺失。Google 无法判断页面是否更新，会降低重抓频率。

建议：给所有静态路由与产品页补 lastmod（可用内容文件 mtime 或 Git 提交时间作为来源），并保证不写未来时间。1691 条 URL 还建议拆成 sitemap index（blog / help-center / guides / products-keyword 分文件），避免单一 200KB 文件整体重下。

P1-2 内容内部链接为零 — 最便宜的增长空间

内容集合篇数零内链篇均正文内链数
Blog（英文）1010 / 100.0
Help Center（英文）2928 / 29≈0.03

结果是每个页面都是孤岛：权重无法流向产品页 / guides，主题聚类无法形成，Google 难以判断站点主次。首页也只有 26 个内部链接。

建议：

  • 在 MDX 组件库里加一个 <RelatedLinks />，让每篇文章底部自动挂载 3–5 条同主题链接 + 1 条产品/CTA 链接，按 frontmatter 的 tags 自动匹配——一次性解决全部内容。
  • 把「每篇新正文至少 3 条站内链接」写进 validate-content.mjs，和现有「必填 frontmatter」同级阻断。
  • 优先给 guides（73 个 URL）之间建立集群互链，这是最有商业价值的资产。

P1-3 OG 图全站只有一张 logo

1691 个页面的 og:image 都是 https://ciwi.ai/logo-150.png。分享到社交、Slack、微信时全部显示同一个 logo，社交 CTR 基本浪费。

建议：用 next/og（ImageResponse）做动态 OG 图：标题 + 分类 + 品牌，部署成本不高，可与 P1-4 的 RSS 一起做。注意你现在 images.unoptimized: true 不影响 OG 生成。

P1-4 缺少 RSS feed，且 affiliate 页面可被抓取

  • blog.ciwi.ai 的 /rss 已被 301 到 /blog/，等于主动放弃了 RSS 这一分发渠道（对 SEO 工具、聚合站、AI 爬虫都有价值）。建议新增 /rss.xml 并加入 llms.txt。
  • /affiliate、/affiliate/dashboard、/affiliate/login、/affiliate/register 均未设置 noindex，且页面含会话与账户信息。虽然不在 sitemap，但仍可被抓取。建议补 noIndex: true，与你对 Chinese 法务页的做法保持一致。

P1-5 缺少自定义 404 页

请求 /this-page-does-not-exist/ 返回状态码 404（正确），但页面没有 title 标签、没有站内导航，用户/爬虫落到一堵墙。仓库没有 not-found.tsx 与 error.tsx。

建议：补 src/app/not-found.tsx，含搜索框 + 热门入口（products / guides / help-center）+ FinalCtaSection，并输出 noindex metadata。别忘了 zh-cn 版本。

六、已经做对的部分（不要改）

  • robots.txt 规范：Allow: / + Disallow: /api/ + Host + Sitemap 四项齐全，且用单一 User-Agent: * 组避免 specificity 覆盖问题。
  • canonical + hreflang 三标签全覆盖：en / zh-CN / x-default 首尾互相指向，抽样三个层级页面（首页 / 列表页 / 程序化详情页）均正确。（注意 Next.js 输出为 hrefLang 驼峰，HTML 属性大小写不敏感，爬虫解析正常。）
  • URL 卫生 Excellent：1691 条 URL 零重复、全部 HTTPS、统一尾斜杠、无 www、无重定向源地址、无双斜杠。/blog → /blog/ 返回 308，www.ciwi.ai → ciwi.ai 返回 301。
  • 结构化数据覆盖广：27 个模板带 JSON-LD，含 BreadcrumbList + WebPage @graph 结构，层级正确。
  • 元数据 100% 覆盖：43/43 page.tsx 都有 metadata 处理，且统一走 buildPageMetadata，无硬编码。
  • 多语言是独立版本而非自动回退：这是很多 i18n 站踩的坑，你们从内容层避免了。
  • llms.txt 已经上线：面向 AI 爬虫的前瞻性投入，继续保持。
  • CI 三层守门全部通过：seo:check、content:validate、seo:artifacts 均已通过。

七、本次已修复并验证

问题改动验证结果
P0-2 description 超限 src/lib/seo/metadata.ts 新增 truncateDescription()：中文字符按 2 单位计宽，优先在句末截断、其次词边界，统一预算 155 单位，并作用于 buildPageMetadata 的 description 输出。 本地生产渲染实测：首页 204 → 122 字符；关键词页 358 → 100 字符；关键词索引 → 121。canonical 与三个 hreflang 均未受影响。

回归防护 新增 scripts/seo-description.test.mjs（6 个用例），覆盖中英截断、词边界、空值、canonical/hreflang 不受影响、noindex 输出。 6/6 通过。

全量校验：lint 通过（仅 1 条既有 <img> 警告）、seo:check 通过、content:validate 通过、next build 通过、seo:artifacts 通过。

修复过程中新发现（未改动，待决策）：truncateTitleToSERPWidth 的目标宽度写成 480，而每个 ASCII 字符只计 0.52 单位， 相当于允许约 920 个字符 —— 这个函数事实上从未触发过。实测关键词页 title 长达 106 字符（Google 约展示 60 字符）。
但直接调小常量并非正确做法：现模板格式是 {描述性标题} — {关键词}，从尾部截断会把关键词整段丢掉。 正确修法是同时把格式改为 {关键词} — {描述性标题} 并把预算调到约 32 单位。因涉及全站 1691 个 title 的可见变化，需你确认后再动。
