# 内容接入与过渡策略

本文件用于明确博客与帮助中心在官网统一前台改造中的接入方式、阶段策略和实施边界。

目标不是一次性重写所有内容系统，而是在不打断现有内容运营的前提下，把前台品牌体验逐步统一到 `ciwi-web`。

## 1. 总体原则

- 前台统一：用户最终看到的品牌层尽量由 `ciwi-web` 承担。
- 后台可分：Ghost 可以继续做博客编辑后台，帮助中心可以暂时保留现有静态产物。
- 渐进迁移：优先迁移高价值入口和高流量页面，不做一次性大迁移。
- SEO 稳定：已有 URL 轻易不废弃，迁移时优先做 301 或 canonical 策略。
- 内容复用：避免同时维护两套相同内容。

## 2. 当前内容系统现状

### Blog

当前存在两套博客相关资产：

- `blog/`
  - 独立 Ghost 实例
  - 有独立数据库、主题和生产配置
- `ciwi-web/public/blog`
  - 历史 Gatsby 静态构建产物
  - 与 Ghost 当前内容体系并不统一

判断：

- 未来应保留 Ghost，放弃继续维护 `public/blog` 这套历史静态产物。
- `public/blog` 只可作为历史过渡资源，不应继续作为主方案扩展。

### Help Center

当前帮助中心位于：

- `ciwi-web/public/help-center`

它是一套独立静态文档产物，内容量较大，且目前仍有稳定 URL 结构。

判断：

- 不适合一期全部重写。
- 应优先保留 URL 与内容可访问性，再逐步统一视觉和前台入口。

## 3. 推荐目标状态

### Blog 目标状态

- 内容编辑后台：Ghost
- 最终前台渲染：Next.js
- URL 目标：`/blog`、`/blog/[slug]`
- 品牌控制：官网统一导航、页脚、CTA、相关文章和产品回流模块

### Help Center 目标状态

- 短期：保留现有静态文档站
- 中期：统一入口、统一导航和视觉外层
- 长期：迁移到统一前台文档体系，或重建为同一设计语言下的 docs 前台

## 4. Blog 迁移策略

### Phase 0：停止扩展旧静态博客

执行原则：

- 不再向 `ciwi-web/public/blog` 投入新内容
- 不再把它视为未来博客前台来源
- 后续博客统一以 Ghost 为源

### Phase 1：统一官网入口，保留 Ghost 前台

一期建议：

- 官网先新增 `/blog` 入口页
- 资源中心与首页内容模块直接引导到博客内容
- Ghost 仍可暂时继续承担真实文章详情页前台

当前状态更新：

- `/blog` 入口页已经落地。
- Ghost 已发布文章已通过构建期静态内容映射接入站内 `/blog/[slug]` 页面。
- 当前站内文章页仍保留原始 Ghost 链接，作为内容来源和过渡手段。
- 站内 Blog 详情页已补 TOC、section anchor、基础 JSON-LD 与相关文章入口。

适合这样做的原因：

- 对当前运营最小扰动
- 开发量可控
- 可以先把品牌总入口统一起来

Phase 1 的建议表现：

- 首页展示最新 3 到 5 篇文章入口
- Resources Hub 统一展示 Blog、Help Center、Compare、Cases
- `Blog` 一级入口可先作为聚合落地页

### Phase 2：Next 接管 Blog 列表页与详情页前台

推荐方向：

- `ciwi-web` 实现 `/blog` 和 `/blog/[slug]`
- 内容通过 Ghost Content API 获取
- Ghost 仅作为内容后台

当前实现程度：

- 路由层面已经实现 `/blog` 和 `/blog/[slug]`
- 但内容获取层尚未接通 Ghost Content API
- 当前使用的是构建期静态内容映射，适合作为早期统一前台阶段的过渡方案

这一步完成后：

- Blog 与官网完全统一品牌语言
- 页面模板、SEO、相关文章、产品回流都由前台控制
- 后续专题页、标签页、作者页扩展成本明显降低

### Phase 3：统一 Blog 主域或子域策略

后续可选：

- 保留 `blog.ciwi.ai`，但由 Next 前台承接
- 或将博客并入主站路径 `/blog/*`
- 二者择一，不建议长期双前台并存

推荐：

- 长期优先统一到主站路径 `/blog/*`

原因：

- 品牌统一更彻底
- 权重与内链集中
- 用户不会感知切站

## 5. Help Center 过渡策略

### Phase 1：保留现有静态帮助中心，统一入口

一期建议：

- 保留 `public/help-center` 的现有静态内容
- 官网 `Resources` 中明确提供 Help Center 入口
- 在官网首页或资源页展示热门问题入口

这一步的原则：

- 不碰大量历史文档正文
- 不打断现有支持内容访问
- 先解决“找得到”和“导得回”两个问题

### Phase 2：统一帮助中心 Landing Page

建议做法：

- 新建 Next 前台的 `/help-center`
- 作为帮助中心统一入口页
- 聚合热门分类、热门文章、产品入口、搜索入口

当前状态更新：

- `/help-center` 聚合入口页已经落地
- 已整理首批高价值文档入口，并纳入官网资源系统
- 当前已开始把首批高价值文档详情页迁入 Next 前台模板
- 已为已迁入的帮助文档详情页补 TOC、section anchor、TechArticle schema，并在 FAQ 型页面补 FAQ schema
- 但帮助中心整体仍处于“入口统一 + 部分详情页迁移”的过渡阶段

此时文章详情页可以暂时仍跳到旧静态文档。

### Phase 3：逐步迁移高价值文档

优先迁移：

- 流量最高的 FAQ
- 高转化相关文档
- 与产品演示和定价强相关的说明页

暂不迁移：

- 长尾低流量文档
- 纯操作步骤但访问量极低的历史内容

### Phase 4：统一文档前台

长期目标：

- 文章列表、分类、正文页都迁入统一前台
- 保留老地址跳转关系
- 搜索、导航、CTA、样式统一

## 6. 一期实施建议

### Blog

一期具体建议：

- 新增 `Resources` 页面
- 首页引入 Blog 内容模块
- 规划 `/blog` 路由，但可以先做聚合入口页
- Ghost 详情页短期保留

当前实际进度：

- `Resources` 已落地
- 首页已接入 Blog 内容模块
- `/blog` 与 `/blog/[slug]` 已落地
- 详情页已由 Next 前台承接，但底层内容源仍是手工映射过渡层
- Blog 详情页已具备目录、锚点、基础结构化数据与站内资源回流能力

### Help Center

一期具体建议：

- 保留旧帮助中心静态页面
- 新增 `/help-center` 聚合入口页
- 展示热门分类与热门问题
- 明确帮助中心与产品页的回流关系

当前实际进度：

- `/help-center` 聚合入口页已落地
- 已整理首批高价值帮助文档入口
- 产品页、资源页和帮助中心之间已有基础回流链接
- 首批高价值帮助文档详情页已开始由 Next 前台承接
- 当前已具备文档目录、正文锚点与 FAQ / 技术文章 schema 的基础层

## 7. URL 与 SEO 原则

### Blog

- Ghost 当前真实文章 URL 不应直接废弃
- 新旧前台并存阶段，避免重复收录
- 一旦 Next 前台接管详情页，应统一 canonical
- 当前 Blog 详情页已输出 canonical 和基础 JSON-LD，后续重点转向内容源同步与 canonical 收敛策略

### Help Center

- 当前已有文档 URL 尽量保留
- 高流量文章迁移后做 301
- 不建议先大规模改 slug
- 对 FAQ 型帮助文档，应优先补 FAQ schema 和产品回流模块，提升长尾搜索承接质量

## 8. 风险与限制

### Blog 风险

- Ghost 与旧 Gatsby 静态博客同时存在，容易造成内容源混乱
- 若不尽快收敛，后续 SEO 和内容维护会继续分裂

### Help Center 风险

- 当前帮助中心是静态产物，不是结构化前台代码
- 若缺少源站工程，全文统一样式改造成本较高

## 9. 最终建议

结论很明确：

- Blog：优先收敛为 “Ghost 后台 + Next 前台”
- Help Center：优先做统一入口，后做逐步前台迁移

这样做的好处是：

- 不阻断当前内容运营
- 不一次性重写所有系统
- 能最快把用户感知统一到一个品牌前台里
